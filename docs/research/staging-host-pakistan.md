# Staging host research: latency-to-Lahore, managed PostGIS + Redis, deploy path

Resolves: https://github.com/hedonarc/foodio/issues/88

Scope: pick a staging host for the `foodio-backend` NestJS service. Hard
requirements: managed/easy Postgres **with PostGIS**, managed Redis,
lowest practical latency to Lahore/Pakistan, hobby-tier monthly cost
(near-zero traffic), and a working GitHub Actions → deploy path.

## Ranked recommendation

### Winner: Fly.io (app) + Supabase Mumbai (Postgres/PostGIS) + Upstash (Redis)

Reasoning:

- **Latency**: this is the only combination that can put the actual compute _and_ the database in Mumbai (`bom`), the lowest-RTT region to Lahore in this whole comparison (~35-40ms, the only inferred number with a directly relevant published data point behind it). AWS Mumbai ties on latency but costs more and requires far more CI/CD plumbing for a near-zero-traffic staging box.
- **PostGIS**: Supabase's managed Postgres bundles PostGIS as a standard extension, and Fly Machines can run `postgis/postgis` directly if a self-hosted fallback is ever needed.
- **Redis**: Upstash is Fly's own documented Redis partner (`fly redis create`), so the app and cache provisioning stay in one CLI/workflow.
- **Cost**: Fly hobby app (~$2-5/mo) + Supabase free tier (with a scheduled keep-alive ping to dodge the 1-week pause, since staging isn't "no traffic" so much as "low traffic") + Upstash free tier (256MB/500K commands, plenty for staging) lands at **roughly $2-5/mo**, with a clean upgrade path (Supabase Pro $25/mo) if the free tier's pause behavior becomes annoying.
- **Deploy path**: `flyctl deploy --remote-only` in a GitHub Actions job (official `superfly/flyctl-actions`) is close to zero-ceremony — a few lines of YAML, no Terraform/CDK, no SSH key management.

### Runner-up: Render (Singapore) — web service + managed Postgres + Key Value

Reasoning: single-vendor simplicity (one dashboard, one bill, `render.yaml` blueprint auto-deploys on push with no custom GitHub Action required at all), PostGIS confirmed supported, Redis-compatible Key Value included natively. The tradeoff is real: Render's nearest region is Singapore, not Mumbai, so inferred RTT to Lahore (~~65-90ms) is roughly double Fly+Supabase's Mumbai path, and the all-in cost (~~$24-30/mo) is higher than the winner's near-zero footprint. Pick this if the team would rather pay a flat, predictable bill and avoid juggling three vendors, and 60-90ms is acceptable for a _staging_ environment (as opposed to production).

**Explicitly not recommended for staging:** Railway (no Asia region at all — inferred 150-250ms is the worst in the set) and raw AWS/Hetzner (both viable, but both require the most CI/CD and infra plumbing for a environment whose whole point is to be cheap and low-effort).

## What to do next

1. Spin up a Fly.io app in `bom` (Mumbai) for `foodio-backend` staging; confirm `fly regions list` still shows `bom` as available for the account's plan.
2. Create a Supabase project pinned to the Mumbai (`ap-south-1`) region, run `CREATE EXTENSION postgis;`, and set up a low-frequency scheduled GitHub Actions job (or Supabase's own cron) that pings the DB to prevent the free-tier 1-week pause.
3. Create an Upstash Redis database (Singapore or global, since Mumbai isn't offered) via `fly redis create` so it's wired into the Fly app's secrets automatically.
4. Add a `.github/workflows/deploy-staging.yml` using `superfly/flyctl-actions@v1` (`flyctl deploy --remote-only`) gated on pushes to `main` or a `staging` branch, with `FLY_API_TOKEN`, Supabase connection string, and Upstash Redis URL as repo/environment secrets.
5. Do a real ping test from a Pakistan-based vantage point (or a Lahore-region synthetic monitor) once the app is live — the 35-40ms figure used above is inferred from Fly's own community latency thread, not a controlled measurement from this project, and should be confirmed before it's used to justify a production decision later.
6. Revisit this doc if/when production sizing is discussed — production may justify AWS ap-south-1 (Mumbai RDS + ElastiCache) for tighter SLAs, VPC isolation, and reserved-instance pricing, none of which matter for a near-zero-traffic staging box.
